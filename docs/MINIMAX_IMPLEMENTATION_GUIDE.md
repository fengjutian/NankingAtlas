# MiniMax 开发执行手册

项目：Nanking Atlas（金陵风物志）  
适用对象：MiniMax 编码模型及使用 MiniMax 的自动化开发代理  
文档状态：强制执行基线  
更新日期：2026-10-09

## 1. 文档用途

本手册用于约束 MiniMax 严格按照 Nanking Atlas 的既定需求、架构和验收标准实施工程任务。它不是产品需求的替代品。

MiniMax 开始任何任务前必须依次完整阅读：

1. `AGENTS.md`：仓库级强制规则。
2. `docs/PRODUCT_REQUIREMENTS.md`：产品范围和原始验收依据。
3. `docs/TECHNICAL_IMPLEMENTATION.md`：已确定的技术实现方案。
4. `docs/IMPLEMENTATION_BACKLOG.md`：任务编号、依赖和阶段验收。
5. 当前任务涉及的代码、测试、迁移和局部说明。

文档冲突时优先级为：用户本轮明确指令 → `AGENTS.md` → 产品需求 → 技术方案 → Backlog。发现冲突必须暂停冲突部分并汇报，不能自行猜测或静默改写需求。

## 2. MiniMax 的工作目标

MiniMax 的目标不是快速生成大量页面，而是按可验证的垂直切片建设一个可运营、可审计、可恢复的文化内容平台。

每次任务必须同时考虑：

- 用户实际可用的功能。
- 服务端权限和数据完整性。
- 历史资料来源与媒体版权。
- 错误、空数据、加载、权限不足和依赖失败状态。
- 自动化测试和人工验收方式。
- 数据库迁移、部署及回滚影响。

## 3. 固定技术栈

MiniMax 不得自行替换或绕开以下选型：

| 范围 | 固定选型 |
| --- | --- |
| 工作区 | pnpm workspace、Turborepo |
| 公开站 | Next.js、React、TypeScript、Tailwind CSS |
| 管理后台 | React、Vite、TypeScript、shadcn/ui |
| API | NestJS、REST、OpenAPI |
| 数据库 | PostgreSQL、PostGIS |
| ORM | Prisma；PostGIS 特性允许受审查的原生 SQL |
| 富文本 | Tiptap JSON 文档 |
| 地图 | Leaflet |
| 文件 | S3 兼容对象存储 |
| 首期搜索 | PostgreSQL、`pg_trgm` |
| 测试 | Vitest、NestJS integration、Playwright |

未经维护者批准和 ADR，不得引入微服务、消息队列、Elasticsearch、第二数据库、第二 ORM 或另一套身份系统。

## 4. 每轮执行流程

### 4.1 开始前

MiniMax 必须：

1. 查看 Git 状态并保护用户已有改动。
2. 定位一个 Backlog 编号，说明本轮只完成什么。
3. 读取相关代码，不得仅根据文件名猜测实现。
4. 列出明确验收条件、依赖和风险。
5. 检查任务是否需要外部服务、凭据、生产权限或业务决定。

若任务会改变架构、产生费用、连接生产、破坏数据、发布线上或使用版权不明素材，必须先请求人工确认。

### 4.2 实现中

- 一次完成一个可测试切片，避免同时铺开大量半成品。
- 先确定契约和业务规则，再实现服务端，最后接入界面。
- 数据库变更必须创建迁移和迁移测试。
- API 变更必须更新 OpenAPI、生成客户端和契约测试。
- 新增权限动作必须加入服务端 guard、审计和越权测试。
- UI 必须覆盖 loading、empty、error、forbidden、conflict 和 success。
- 不得用硬编码返回、静态 JSON 或 localStorage 冒充后端功能。
- 不得把演示内容写成已经核验的南京史实。

### 4.3 完成前

按受影响范围运行：

```text
pnpm format:check
pnpm lint
pnpm typecheck
pnpm test
pnpm build
```

涉及数据库时还必须验证：

- 空数据库能完整执行迁移。
- 已有测试数据能升级。
- 约束、索引和 PostGIS 查询实际有效。
- 回滚或 expand/contract 方案明确。

涉及核心流程时运行对应 Playwright E2E。无法运行的检查必须写明原因，不能写“理论上可以通过”。

## 5. 强制实现原则

### 5.1 权限

- Web 和 Admin 永远不能直接连接数据库。
- 所有后台写入由 API 认证和授权。
- Editor 可以写草稿和送审，但不能审核或发布。
- Reviewer/Admin 的发布动作也必须通过 publication readiness。
- 前端按钮是否显示不构成权限控制。
- 未认证返回 401；已认证但权限不足返回 403；并避免泄露资源存在性。

### 5.2 内容审核

固定状态机：

```text
DRAFT → IN_REVIEW → APPROVED → PUBLISHED → ARCHIVED
          ↓              ↓
        DRAFT          DRAFT
```

任何状态跳转必须由领域服务验证，并在同一事务内写入：

- 内容当前版本。
- revision 快照。
- review action。
- audit log。

退回必须填写原因。普通业务接口不能修改或删除历史审核记录。

### 5.3 历史与版权

- 不得编造历史事实、日期、人物关系、地址、坐标、引用和来源。
- 未核实内容只能使用 `UNVERIFIED/PARTIAL/DISPUTED`。
- 民间传说和编辑推断不能展示为已证实史实。
- 需求文档中的图片仅供设计参考，不能作为上线素材。
- 媒体缺少许可、署名、alt 或版权状态时不得发布。
- 坐标不可靠时保持为空或区域级，不能猜测精确坐标。

### 5.4 安全

- 密码使用 Argon2id，不得明文或可逆保存。
- refresh token 只保存哈希并支持旋转、撤销和过期。
- Cookie、CORS、CSRF、CSP、限流严格按技术方案实现。
- DTO 必须白名单校验，未知字段拒绝。
- 富文本节点、mark、URL 协议必须白名单净化。
- SQL 参数化；上传验证 MIME、魔数、大小和尺寸。
- 生产错误不返回堆栈、SQL、内部路径或秘密。
- 日志不得记录密码、token、Cookie、密钥或完整个人信息。

### 5.5 数据一致性

- 生产 schema 只能通过版本化迁移变更。
- 并发更新使用 version 乐观锁，冲突返回 409。
- revision、review action、audit log 只增不改。
- 发布检查不能被 query/body 参数关闭。
- 缓存和搜索索引不是权威数据源。
- Redis 在 MVP 中是可选优化，不得成为基本功能的必要条件。

## 6. 禁止使用的“捷径”

MiniMax 不得：

- 用 `any`、`@ts-ignore`、空 catch 或批量非空断言隐藏类型/运行时问题。
- 删除、跳过或弱化测试以制造通过结果。
- 修改验收条件来匹配当前实现。
- 用 Mock、静态数组或假 API 宣称数据库和发布链路完成。
- 只实现正常路径，不处理错误、权限和并发。
- 擅自清空数据库、重置迁移、覆盖用户文件或丢弃工作区修改。
- 在没有运行验证时声称构建、测试或部署成功。
- 把文档、界面原型或占位按钮描述成完整业务实现。
- 自行购买服务、创建付费实例、改 DNS 或发布生产环境。

## 7. 任务输入模板

建议每次给 MiniMax 一个 Backlog 编号，不要直接要求“一次完成整个项目”。可复制以下模板：

```text
你正在开发 Nanking Atlas（金陵风物志）。

先完整阅读：
1. AGENTS.md
2. docs/PRODUCT_REQUIREMENTS.md
3. docs/TECHNICAL_IMPLEMENTATION.md
4. docs/IMPLEMENTATION_BACKLOG.md
5. docs/MINIMAX_IMPLEMENTATION_GUIDE.md

本次任务：<Backlog 编号和名称>
允许修改范围：<目录或模块>
本次不做：<明确排除项>

要求：
- 先检查现有实现和 Git 状态。
- 在实现前列出验收条件和可能影响。
- 完成代码、校验、错误处理、权限、测试和必要文档。
- 实际运行受影响的 lint、typecheck、test、build。
- 不得伪造历史资料、测试结果或完成状态。
- 不得擅自改变架构或技术栈。
- 按本手册规定的交付模板汇报。
```

## 8. P0 启动提示词

首次让 MiniMax 开始工程实现时，可直接使用：

```text
严格按照仓库 AGENTS.md 与 docs/MINIMAX_IMPLEMENTATION_GUIDE.md 执行。

本轮只实施 P0-01 到 P0-03：
- pnpm workspace 与 Turborepo 根骨架；
- apps/web、apps/admin、apps/api 三个可独立运行应用的最小骨架；
- 共享 TypeScript strict、ESLint、Prettier 和环境变量校验。

不得提前实现业务页面、数据库模型或外部服务，不得使用 mock 宣称业务完成。
先检查当前仓库，提出精确文件计划；随后直接实现并运行 format、lint、typecheck、test、build。
如果环境缺少依赖或网络权限，如实汇报并保留可复现命令。
最后按 MiniMax 交付模板输出结果。
```

## 9. 交付输出模板

MiniMax 每轮必须使用以下结构：

```text
任务编号与范围：

已实现：
- <具体功能与行为>

未实现/明确排除：
- <本轮没有覆盖的内容>

数据与迁移：
- <新增表、字段、迁移、兼容性；没有则写“无”>

安全与权限：
- <鉴权、授权、校验、审计；不适用则说明>

验证命令及真实结果：
- `<命令>`：通过/失败/未运行
- 失败或未运行原因：<原因>

变更文件：
- `<文件>`：<修改目的>

风险与阻塞：
- <风险、外部依赖、未验证事项>

建议下一步：
- <下一个 Backlog 编号，不得把建议写成已完成>
```

## 10. MiniMax 自检清单

每次提交前逐项回答：

- [ ] 是否完整读取了相关需求和现有代码？
- [ ] 是否只处理了声明的任务范围？
- [ ] 是否保护了用户已有改动？
- [ ] 是否引入了未经批准的架构或依赖？
- [ ] 是否存在 mock/占位实现却被描述为完成？
- [ ] 是否覆盖身份、权限、输入错误、空状态和并发？
- [ ] 是否保存来源、版权、版本和审计信息？
- [ ] 是否可能发布未经核实的历史内容或坐标？
- [ ] 是否有真实测试证明验收条件？
- [ ] 是否如实记录失败和未运行项目？
- [ ] 是否检查了秘密、个人信息和日志泄露？
- [ ] 是否更新了相关契约、迁移和文档？

任一必要项为“否”时，任务不得标记完成。

## 11. 阶段验收门禁

MiniMax 不得跨过未完成的阶段门禁：

- P0 门禁：三个应用可独立运行；根级质量命令通过；开发配置无秘密。
- P1 门禁：真实数据库和服务端权限有效；审核发布链路通过集成/E2E；审计可追溯。
- P2 门禁：发布内容从后台到公开站闭环；SEO、撤回和响应式验证通过。
- P3 门禁：真实 PostGIS bbox 查询；地图/列表联动和失败降级通过。
- P4 门禁：安全、性能、监控、备份恢复和上线 runbook 有真实证据。

前一阶段未满足时，可以为后续做不破坏兼容性的准备，但不能宣称后续阶段已经交付。

## 12. 需要人工决策的事项

遇到以下事项，MiniMax 只能给出选项与影响，不能代替用户决定：

- API、PostgreSQL、对象存储和邮件服务供应商。
- 正式域名、付费套餐与生产部署。
- 地图供应商、中国大陆地图合规和坐标策略。
- 版权争议、合理使用判断和正式法律文本。
- 史实争议的最终编辑结论。
- 备份保留期、RPO/RTO、日志保留期和告警负责人。
- 任何破坏性迁移、生产数据导入或永久删除。

MiniMax 应先完成不依赖这些决定的代码，并把未决事项集中列入交付报告。
